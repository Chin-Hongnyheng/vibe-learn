# 2.9 — Supabase User-Domain Schema + API Layer

## Goal

Extend the Supabase integration to cover the user-domain tables defined in
`src/types/users.ts`: `users`, `lessons`, `progress`, `enrollments`, and
`notifications`. Deliver:

1. SQL schema + RLS policies (appended to a new migration file).
2. `src/lib/api/users.ts` — typed Supabase fetch functions for the
   **public / lesson** surface. Progress, enrollment, and notification reads
   are stubbed as commented-out placeholders because they require the Express
   backend (auth-gated, write-only via server route per AGENTS.md §4 §8).

---

## Architecture Boundary — Critical

| Table | Read from frontend? | Write from frontend? | Notes |
|---|---|---|---|
| `lessons` | ✅ anon OK | ❌ | Public catalog content |
| `users` | ❌ | ❌ | Synced from Clerk via backend webhook |
| `progress` | ❌ | ❌ | Read + write via Express backend only |
| `enrollments` | ❌ | ❌ | Write via Express backend; read via backend |
| `notifications` | ❌ | ❌ | Backend concern; presentational for now |

The frontend's `src/lib/api/users.ts` file will only implement the `lessons`
fetch functions. All others are documented stubs pointing to the future
backend endpoint.

## Decisions & Assumptions

1. **SQL file**: Create `src/lib/supabase-users-schema.sql` (do not modify the
   existing seed — keep schemas separate for clarity).

2. **`lessons` table**:
   ```sql
   create table lessons (
     id bigint primary key generated always as identity,
     module_id bigint references modules(id) on delete cascade,
     title text not null,
     slug text not null unique,
     youtube_video_id text not null,
     notes text,
     position integer not null
   );
   -- RLS: anon SELECT
   ```

3. **`users` table**:
   ```sql
   create table users (
     id text primary key,           -- Clerk User ID
     email text not null,
     first_name text not null,
     last_name text not null,
     avatar_url text,
     created_at timestamptz not null default now(),
     updated_at timestamptz not null default now()
   );
   -- RLS: authenticated users read own row only; no anon reads
   ```

4. **`progress` table**:
   ```sql
   create table progress (
     user_id text references users(id) on delete cascade,
     lesson_id bigint references lessons(id) on delete cascade,
     course_id bigint references courses(id) on delete cascade,
     completed boolean not null default false,
     resume_timestamp integer not null default 0,  -- seconds
     completed_at timestamptz,
     updated_at timestamptz not null default now(),
     primary key (user_id, lesson_id)
   );
   -- RLS: authenticated users read/write own rows only
   -- But actual writes go through the Express backend only (server-side)
   ```

5. **`enrollments` table**:
   ```sql
   create table enrollments (
     user_id text references users(id) on delete cascade,
     course_id bigint references courses(id) on delete cascade,
     enrolled_at timestamptz not null default now(),
     last_accessed_at timestamptz,
     primary key (user_id, course_id)
   );
   -- RLS: authenticated users read own rows only
   ```

6. **`notifications` table**:
   ```sql
   create table notifications (
     id bigint primary key generated always as identity,
     user_id text references users(id) on delete cascade,
     title text not null,
     message text not null,
     read boolean not null default false,
     created_at timestamptz not null default now()
   );
   -- RLS: authenticated users read own rows only
   ```

7. **`src/lib/api/users.ts`**:
   - Implements: `getLessonsByModule(moduleId): Promise<Lesson[]>` and
     `getLessonById(id): Promise<Lesson | null>` — using anon Supabase client.
   - Stubs (commented): `getMyProgress`, `getMyEnrollments`, `getMyNotifications`
     with a JSDoc note pointing to the future backend endpoint.

## Security

- Only `lessons` gets a public anon SELECT policy.
- `users`, `progress`, `enrollments`, `notifications` use
  `auth.uid() = user_id` RLS — preventing any cross-user reads.
- No service role key in frontend code, ever.
